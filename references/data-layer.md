# 数据层范式（拆 / 池）

> 建表、索引、SQL 编写的具体红线（禁外键、禁存储过程、超三表禁 join 等）见 `ali-db-guidelines.md`。

## 1. 读写分离

- 主库负责事务性写入，多个从库负责查询，主从复制同步。
- 适合读多写少业务（互联网业务绝大多数如此）。
- 中间件自动路由：ShardingSphere、MyCAT、ProxySQL、MaxScale。
- 主从延迟问题：强一致读强制走主库；或用版本号/时间戳校验数据新旧。

## 2. 分库分表

触发条件：单表数据量超千万级，索引效率急剧下降；或单库连接/IO 达到极限。

### 拆分方式
- 垂直分库：按业务耦合度拆到不同库实例。
- 垂直分表：大表冷热字段拆分。
- 水平分库分表：按路由策略（取模、范围、哈希）打散到多节点，突破单机 I/O 瓶颈。

### 关键决策
- 分片键选择：既要数据均匀，又要避免跨分片 Join 和跨分片查询。
- 配合分布式 ID 生成器（雪花算法、号段模式）保证全局唯一。
- 分布式事务：优先最终一致（本地消息表、TCC、Saga），避免强一致两阶段提交的性能代价。
- 不苛刻一致性场景可引入 NoSQL（HBase/MongoDB/Cassandra）补充。

## 3. SQL 与索引优化

- 杜绝全表扫描，建立严格索引规范；用执行计划分析慢查询。
- 覆盖索引减少回表；深分页、大关联查询重写 SQL 逻辑。
- 乐观锁替代悲观锁减少锁争用；热点行更新考虑拆分热点。

## 4. 连接池与池化（池）

- 连接池：Druid、HikariCP；连接是昂贵资源，按 DB 负载设合理上限，防止打满连接数。
- 线程池、对象池、HTTP 连接池同理：复用资源，避免频繁创建销毁的 CPU 损耗。
- 典型故障："Too many connections" → 池化管理 + 读写分离 + 分库分表。

## 5. 零拷贝等底层优化

- 文件传输用 sendfile 等零拷贝技术，绕过用户空间拷贝，降低 CPU 与上下文切换开销。
- Netty 等非阻塞 I/O 框架以少量线程支撑海量连接。
