# 架构演进与微服务（拆）

## 1. 标准分层架构

```
接入层(网关/负载均衡) → 应用层 → 缓存层 → 数据层
```

每层职责单一、可独立扩容，这是高并发架构的核心思想。
- 接入层：流量分发、SSL 终止、WAF/IP 黑名单、限流、健康检查。
- 应用层：无状态化（状态外置 Redis 或 JWT），任意机器可处理任意请求，N+1 冗余容错。
- 缓存层：见 caching.md。
- 数据层：最难扩的一层，见 data-layer.md。

## 2. 演进路径

单体 → 垂直扩容 → 读写分离/缓存 → 水平扩容 → 分库分表 → 微服务 → 服务治理。

不要跳级演进：小流量时引入微服务、分库分表纯属过度设计。

## 3. 微服务拆分时机

该拆的信号：
- 部署频率被架构卡住，迭代受阻。
- 团队超过 10 人，协作冲突频繁。
- 不同模块扩容需求差异明显。
- 技术债积累到不可维护。

不该拆：
- 团队只有 3~5 人。
- 业务边界还在快速变化。
- 无监控、日志、CI/CD 等基建支撑。
- 为拆而拆，没有明确痛点。

## 4. 拆分原则

- 按业务域（DDD）：用户、订单、支付、库存各自成服务，高内聚低耦合。
- 单一职责：一个服务做好一件事，不跨域操作他服务数据。
- 独立部署：独立仓库、独立 CI/CD、独立发布节奏。
- 数据隔离：每服务私有数据库，禁止共享库，通过 API 交换数据。

## 5. 服务治理

- 服务发现：注册中心（Nacos、Consul、Eureka、K8s Service）解决"谁在哪"。
- 通信：同步 RPC/HTTP（内部调用）+ 异步事件（MQ，跨服务解耦）。
- 容错：超时、重试（指数退避）、熔断、降级，见 stability.md。
- CQRS：读写分离的命令/查询模式，适合读多写少的聚合优化。

## 6. 权衡提醒

微服务的代价：分布式事务、网络延迟、数据一致性、运维复杂度。
拆分收益必须明显大于这些代价，否则保持模块化的单体。
